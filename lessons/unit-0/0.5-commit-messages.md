# Lesson 0.5: Writing Clear Commit Messages

**Unit 0: Groundwork** · About 1 hour

## Why this comes next

You've made a few commits now. Each one has a message, the caption on the picture. Today you'll read your repo's history, see why good captions matter, and practise writing them.

This matters more than it sounds. On the real project, your commit history is how I'll follow your work, and how you'll find out what changed, and when, months from now.

## Objectives

By the end of this lesson, you can:

- Show your repo's history with `git log` and `git log --oneline`, and quit the list with **q**.
- Rewrite a vague commit message so it starts with a verb, says what changed, and is about 50 characters or fewer.
- Split a message that describes two changes into one message for each commit.
- See your uncommitted changes with `git diff` before you commit.
- Write a commit message with a short first line and a longer explanation, in VS Code.

## Step 2: Read your history

Git keeps a list of every commit. To see it, run:

```
git log
```

Each commit shows four things:

- A long ID, after the word `commit`
- Who made it (`Author`)
- When (`Date`)
- The message

The newest commit is at the top. You'll see yours and mine mixed together.

> [!NOTE]
> **If you see `:` at the bottom of the screen**, the list is longer than your screen. Press **Space** to see more, and **q** to quit and get your terminal back. This works anywhere Git shows you a long list.

That's a lot of detail. For a short version, one commit per line:

```
git log --oneline
```

Now each commit is just a short ID and its message. Find `update journal`. Its ID starts with `c00fcb3`, the same as the end of the link you sent me after Lesson 0.3. That link pointed to this commit.

Read down the list. It tells the story of your repo so far, one caption at a time.

> [!TIP]
> **Some of my messages start with `docs:` or `fix:`.** That's a style some teams use, called *Conventional Commits*. The word before the `:` says what kind of change it is. You don't need it yet. You'll learn it when you work on the real project.

## Step 3: What makes a message clear

Look at `update journal` again. In Lesson 0.3 I gave you `Update journal` to type. That was fine for a first commit, but it's vague. A month from now, which journal entry was it? What was in it?

A clear message follows four rules.

**1. Start with a verb, like a command.** Write `Add journal entry`, not `Added journal entry` or `Adding journal entry`. A good test: your message should finish this sentence.

> *If you use this commit, it will* ___

*If you use this commit, it will* **Add journal entry for Lesson 0.3.** ✓

Useful verbs: *Add*, *Fix*, *Update*, *Remove*, *Rename*, *Move*.

**2. Say what changed.** `Fix typo` is OK. `Fix typo in journal date` is better. Someone reading only the message should know which part of the repo changed.

**3. Keep it short.** Aim for about 50 characters: a short phrase, not a paragraph. Start with a capital letter, and leave off the full stop at the end.

**4. One change per commit.** If your message needs the word *and*, it might be two commits. `Add command notes and fix journal date` is two changes. Commit each one by itself, and each gets its own clear message.

Now look at your own history again. Two of your messages from Lesson 0.4 make good examples:

- `Add journal entry for Lesson 4.0` is nearly perfect. It starts with a verb, says what changed, and is short. The only problem is the number: it was Lesson **0.4**. A message has to be accurate as well as clear.
- `add first commit` was the commit where you ticked the checklist in Lesson 0.3. The message doesn't say that. Something like `Tick Lesson 0.3 checklist` would have.

You can't change those messages now, and you don't need to. Just write the next ones better.

## Step 5: See what changed before you commit

Before you write a message, it helps to look at what you're about to commit. Open your notes from Lesson 0.4:

```
code commands.md
```

First, a fix. I read your table, and it's good: short, and in your own words. I spotted three small mistakes, though:

- The `cd..` row. How many folders does it really go up? And check how you typed the command.
- The `mdir` row. Check the spelling of the command.
- One row appears twice.

Fix all three and save. Then run:

```
git diff
```

`git diff` shows the changes you haven't committed yet. Lines starting with `+`, in green, are lines you added. Lines starting with `-`, in red, are lines you removed. Press **q** if you see `:` at the bottom.

Check that the diff shows only your three fixes, then commit them. Write the message yourself this time, following the four rules:

```
git add commands.md
git commit -m "your message here"
```

Now a second change. Add two rows to your table, in your own words:

- `git log`
- `git log --oneline`

Save the file and run `git diff` again. This time you should see only the two new rows.

Fixing mistakes and adding rows are two different changes, so they get two commits, even though they're in the same file. Commit this one:

```
git add commands.md
git commit -m "Add git log commands to command notes"
```

## Step 6: A message with more to say

Sometimes a short message isn't enough. You want to explain *why*, or add details. Git has room for that: a short first line, a blank line, then as much as you like.

Remember your question about `core.editor`? This is where it helps. Commit your practice file **without** `-m`:

```
git add commit-messages.md
git commit
```

A new tab opens in VS Code, and the terminal waits. The tab has some lines starting with `#`. Git ignores those. They're just there to remind you what you're committing.

On the **first line** of the tab, type a short message, following the four rules. Leave the **second line** empty. On the **third line**, write a sentence or two about the exercise: what you found hardest, or which rule you think matters most. For example:

```
Add commit message practice

Rewrote six bad messages. Saying exactly what changed was the
hardest part, so rule 2 feels the most useful.
```

Write your own. Don't copy this one.

Save (**Ctrl + S**) and close the tab. The terminal finishes the commit. Check it:

```
git log
```

Your message is at the top, with both parts. Now try:

```
git log --oneline
```

Only the first line shows. That's why the first line should make sense on its own.

## If something goes wrong

- **The terminal looks stuck, with `:` at the bottom:** Git is showing a long list. Press **q**.
- **`Aborting commit due to empty commit message`:** you closed the VS Code tab without typing a message, or without saving. Nothing was committed. Run `git commit` again.
- **Typed a message you don't like, and already committed?** Leave it. Don't try to change commits yet. Write the next one better.
- **`git diff` shows nothing:** either you haven't saved the file, or you already ran `git add`. Save it, or try `git diff --staged` to see what's on the stage.
